Matplotlib・Cartopyの描画支援に向くlocal LLMは？

作成日: 2026-08-07

カテゴリ: ai-coding-agents

元の質問

local LLMで、pythonのmatplotlib,cartopyを使った描画を手伝わせるのに適したものは？

回答

32 GB以上のメモリがあるなら、コードを主に直す用途は Qwen3-Coder:30b、生成した図も見せて直す用途は画像入力に対応する Devstral Small 2 が有力です。16 GB級では Qwen2.5-Coder:7b から始めるのが現実的です。モデル名以上に、LLMがスクリプトを実行し、例外・標準出力・保存したPNGを受け取れる環境を用意することが重要です。

用途別の第一候補

環境・用途 候補 選ぶ理由
16 GB級、短いスクリプト Qwen2.5-Coder:7b Ollama版は4.7 GBで32Kコンテキスト。軽さを優先した出発点。
32 GB級、コード生成・修正 Qwen3-Coder:30b Ollama版は19 GB。30.5B総パラメータ・3.3B activeのMoEで、256Kコンテキストとtool callingを備える。
32 GB以上、図も見せたい Devstral Small 2 24B、256Kコンテキストのcoding agent向けモデルで画像入力にも対応する。
大容量メモリ、長い反復作業 Qwen3-Coder-Next 80B総パラメータ・3B active、256Kコンテキスト。OllamaのQ4モデルだけで52 GBある。

上の区分はモデルファイル容量だけでなく、OS、コンテキスト用キャッシュ、Python実行環境にも余裕を残すための実務上の目安です。Qwen3-Coder 30Bの仕様とOllamaでの配布容量は公式のモデルカードとライブラリに記載されています。[1][2]Qwen2.5-CoderのOllama版は7Bが4.7 GB、14Bが9.0 GB、32Bが20 GBです。[3]Qwen3-Coder-Nextは公式モデルカード上で80B総パラメータ・3B active、OllamaのQ4版で52 GBです。[4][5]

なぜ「最強のcoder」だけでは不十分なのか

描画支援には、APIを使ったコード生成、実行エラーを受けた修正、生成図を見た視覚的な修正という三つの能力があります。テキスト専用coderは最初の二つに向きますが、「凡例がデータを隠す」「カラーバーが太い」「地図が潰れている」といった問題は、PNGを画像入力できるモデルの方が扱いやすくなります。

Devstral Small 2はcoding agent向けの24Bモデルで、公式発表では画像入力とローカル実行に対応します。[6]テキスト専用モデルを使う場合は、コード担当をQwen3-Coder、画像確認を Qwen3-VL:8b のようなvision-language modelに分ける方法もあります。Qwen3-VLのOllama版には2B、4B、8Bなどが用意されています。[7]

Matplotlib・Cartopyでは実行ループが特に重要

Cartopyでは、axesの見た目を決める projection と、入力データの座標系を伝える transform は別物です。公式チュートリアルも、描画関数へ常に transform を渡すことを安全な方法として勧めています。[8]コードが例外なく終了しても、座標変換を誤ると点や等値線が静かに間違った場所へ描かれます。

Natural Earth由来の海岸線や湖などはCartopyのfeature interfaceから利用できます。[9]完全オフライン運用では初回のデータ取得を想定し、必要なfeatureを事前にキャッシュします。画面のない環境ではMatplotlibの非対話backendでPNGへ保存し、そのファイルをLLMへ戻します。Matplotlib公式文書ではAggが非対話のラスター出力に使われ、savefigで保存できると説明されています。[10]

最小構成はOllamaと実行可能なcoding agent

# 32 GB級の本命
ollama run qwen3-coder:30b

# 16 GB級の軽量案
ollama run qwen2.5-coder:7b

チャット欄へ毎回コードとエラーを貼るより、対応するcoding agentから「ファイルを読む → Pythonを実行する → エラーまたはPNGを確認する → 修正する」を回す方が有効です。Ollamaはtool callingと複数回のagent loopを提供しています。[11]ファイル編集とshell実行は対象ディレクトリを限定し、自動承認を広げすぎない設定にします。

LLMに渡す依頼文の例

この描画スクリプトを修正してください。

目的:
- 緯度経度データをRobinson投影の全球図に描く
- 海岸線と湖を表示し、国境線は表示しない
- 横長、図中テキストは英語、PNGで保存する

必須条件:
- axesのprojectionとデータのtransformを明示的に分ける
- 入力変数のdimensions、coordinates、unitsを実行前に確認する
- 変更後にスクリプトを実行する
- 例外がなくても、保存PNGを確認して位置ずれ、欠け、凡例、
  カラーバー、単位を点検する
- 推測した点と、実データから確認した点を分けて報告する

データを見せる際は、配列だけでなく、xarray.Datasetの表示、変数名、次元順、緯度の昇順・降順、経度範囲、欠測値、単位、期待する地図範囲も渡します。これはモデルの賢さで補う部分ではなく、描画仕様そのものです。

自分の環境で4問だけ評価する

  1. 既存コードへ軸ラベル、単位、細いカラーバーを追加させる。
  2. projectionとtransformを意図的に混同した地図を直させる。
  3. 存在しない変数名や次元順の違いで起きる例外を、実行結果から直させる。
  4. 保存PNGを見せ、文字切れ、凡例の重なり、データ位置を指摘・修正させる。

同じ初期コード、制限時間、最大試行回数で比較し、「最終コードが実行できたか」「地理的に正しいか」「人間の手直し回数」「所要時間」を記録します。一般的なcoding benchmarkより、この小さな実務テストの方が自分のCartopy作業には直接的です。

まとめ

迷ったら、32 GB以上では Qwen3-Coder:30bを実行可能なagentにつなぐ構成から始めます。完成図まで一つのモデルへ見せたいなら Devstral Small 2、16 GB級なら Qwen2.5-Coder:7bが現実的です。大容量環境では Qwen3-Coder-Nextも候補ですが、まずは小さいモデルで実行・画像確認ループを整える方が、Matplotlib・Cartopy支援の品質差を見極めやすくなります。
