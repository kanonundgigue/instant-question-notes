外部ネットワークに接続できないサーバをgit bundleで更新する

作成日: 2026-09-18

カテゴリ: github

元の質問

サーバでの外部ネットワーク接続ができない状況にしばらくなっているが、githubのリポジトリを更新したい。。

Macを経由してGitの履歴を往復させる

サーバがGitHubへ接続できなくても、ネット接続できるMacからSSH・SCPでサーバへアクセスできれば、git bundleで履歴を転送できる。サーバ独自のコミットも維持し、通常のマージとして競合を解消する。bundleはオフラインでGitのオブジェクトと参照を渡す仕組みで、git fetchの入力にできる。[1]

GitHub → Macでfetch → bundleをSCP → サーバでfetch・merge
サーバで競合解消・commit → bundleをSCP → Macでfetch・merge → GitHubへpush

以下は両端末に同じリポジトリがあり、対象ブランチがmaster、Macのリモート名がoriginの例。mainを使う場合は読み替える。user@server.exampleは自分のSSH接続先に置き換える。各コマンドの成功を確認して次へ進み、エラーが出たらその段階で止める。

  • サーバの状態確認と保存
  • Macから最新履歴を転送
  • サーバでマージと競合解消
  • 取り込み結果を確認
  • サーバの変更をMacへ戻す
  • GitHubへpushして確認

1. サーバの状態を確認してコミットを保存する

実行場所：サーバ。マージ前に作業ツリーとブランチを確認する。今回の開始時点はmaster...origin/master [ahead 1]で、未コミット変更はなく、サーバ独自のコミットが1つあった。

cd ~/.dotfiles
git status --short --branch
git branch -vv | cat
git --no-pager log -5 --oneline
git branch backup-before-offline-update-20260918 HEAD

バックアップ用ブランチは現在のコミットを保存する。未コミット変更や未追跡ファイルは保存しないので、それらがある場合は別途バックアップし、必要な変更を整理してコミットするなどしてから進める。バックアップ名の日付は作業日に合わせ、既存のブランチと重複しない名前にする。サーバのorigin/masterは以前取得した情報なので、この時点のahead数から現在のGitHubとの差は判断できない。

2. MacでGitHubの最新履歴を取得して転送する

実行場所：Mac。SSH接続中の端末とは別にMacのターミナルを開く。プロンプトのホスト名で実行場所を確認する。

cd ~/.dotfiles
git fetch origin
git bundle create /tmp/dotfiles-master.bundle refs/remotes/origin/master
scp /tmp/dotfiles-master.bundle user@server.example:/tmp/

このbundleには取得したorigin/masterとそこからたどれる履歴が入る。Macの未コミット変更は含まれない。bundleの検証は形式や必要な履歴を確認するもので、マージ時の競合がないことを保証するものではない。[1]

3. サーバで履歴を取り込んで競合を解消する

実行場所：サーバ。専用の参照offline/masterへ読み込み、その履歴を現在のブランチへ統合する。

cd ~/.dotfiles
git bundle verify /tmp/dotfiles-master.bundle
git fetch /tmp/dotfiles-master.bundle refs/remotes/origin/master:refs/remotes/offline/master
git status --short --branch
git merge --no-edit offline/master

競合が起きるとマージは途中で止まる。今回競合したのは.shell_profileと.zshrcだった。競合ファイルと差分は次で確認する。[2]

git diff --name-only --diff-filter=U
git --no-pager diff -- .shell_profile .zshrc
<<<<<<< HEAD
サーバ側の内容
=======
GitHubから取り込んだ側の内容
>>>>>>> offline/master

競合範囲を意図した最終内容へ編集し、3種類のマーカーを除去する。条件分岐はマーカー外のelseやfiまで含めて整合性を確認する。今回のConda設定では、Mac判定条件とインストール先の存在確認を残し、サーバのMAMBA_ROOT_PREFIXを維持した。実行パス中の$HOMEは展開されるようダブルクォートに直した。これらのホスト別条件やパスは各環境に合わせて判断する。

.zshrcでは、~/.local/bin/envが存在するときだけ読み込み、対象サーバで~/.local/binをPATHの先頭へ置く設定を残した。シェル設定を編集中は現在の接続を維持し、競合中のファイルをsourceして実行しない。

bash -n .shell_profile
# Zshが利用できる環境でのみ実行する
zsh -n .shell_profile
zsh -n .zshrc

grep -nE '^(<<<<<<<|=======|>>>>>>>)' .shell_profile .zshrc
git diff --check

今回のサーバにはZshがなく、zsh: コマンドが見つかりませんとなった。Zshの構文検証はMacなどZshのある環境で行う。Bashの構文チェックはZsh固有構文の代わりにはならない。マーカー検索は出力なしが期待されるが、その場合のgrepの終了コードは1になる。構文チェックと差分チェックはエラーがないことを確認する。構文が正しくても、パスの存在や設定の動作までは保証されない。

確認後、解消したファイルだけをステージしてマージコミットを確定する。バックアップを誤って追加しないよう、対象を明示する。

git add .shell_profile .zshrc
git commit --no-edit

取り消して開始前へ戻したい場合は、マージが未確定の間にgit merge --abortを使う。今回のように開始時の作業ツリーがクリーンな状態で実施する。[2]

4. サーバが転送された最新履歴を含むことを確認する

git status --short --branch
git diff --name-only --diff-filter=U
git merge-base --is-ancestor offline/master HEAD
echo $?

echo $?は直前のコマンドの終了コードを表示するので、間に別のコマンドを挟まず実行する。0ならoffline/masterは現在のHEADの祖先で、転送したGitHubの履歴が含まれている。1は含まれていないことを示し、それ以外はエラーとして調べる。[3]

今回の結果はahead 58、未解消ファイルなし、祖先確認は0だった。origin/masterは更新していないため、ahead数は古い参照との比較になっている。確認の基準には今回更新したoffline/masterを使う。

?? .shell_profile_20260918と?? .zshrc_20260918は手作業で作成した未追跡バックアップだった。これらが残っていても取り込み完了は確認できる。ただし作業ツリーが完全にクリーンとは表現しない。認証情報を含むバックアップは公開対象に追加しない。

5. サーバの変更と競合解消結果をMacへ戻す

実行場所：サーバ。マージコミットを含むmasterをbundleへ保存する。

cd ~/.dotfiles
git bundle create /tmp/dotfiles-server.bundle master

実行場所：Mac。bundleを受け取り、専用の参照へ取り込む。

scp user@server.example:/tmp/dotfiles-server.bundle /tmp/
cd ~/.dotfiles
git status --short --branch
git bundle verify /tmp/dotfiles-server.bundle
git fetch /tmp/dotfiles-server.bundle master:refs/remotes/server/master
git --no-pager log --oneline master..server/master
git --no-pager diff master server/master -- .shell_profile .zshrc

fetchで作られるのはserver/masterという参照で、Macのmasterはまだ更新されない。今回も、この段階でのgit pushはEverything up-to-dateになった。差分を確認し、サーバの設定がMacでも適切か判断してから統合する。

git merge-base --is-ancestor server/master master
echo $?

# 1で、Macの作業ツリーがクリーンなら統合する
git status --short --branch
git merge --ff-only server/master

--ff-onlyはMacのブランチをそのまま先へ進められる場合にだけ成功し、履歴が分岐していれば停止する。停止した場合は差分と履歴を確認して通常のマージを検討する。[2]

git status --short --branch
git merge-base --is-ancestor server/master HEAD
echo $?

最後が0ならMacにもサーバの履歴が含まれる。今回の作業ではここまで確認済み。未追跡バックアップはbundleに含まれず、Macには転送されない。

6. MacからGitHubへpushして反映を確認する

実行場所：Mac。GitHubにもサーバの変更を保存する場合はpushする。今回の会話ではこのpushの成功までは確認していないため、以下は次に行う手順。

git status --short --branch
git push origin master
git rev-parse HEAD
git ls-remote origin refs/heads/master

pushの成功を確認し、2つのコマンドが表示するコミットIDが一致することを確かめる。GitHub側が更新されてpushが拒否された場合は、git fetch originで最新履歴を取得し、状態と差分を確認して統合する。GitHubで追加された変更をサーバにも渡す場合は、再びMacでbundleを作って転送する。

bundleで移るものと、確認できた範囲を区別する

この手順で往復するのは指定した参照からたどれるコミット履歴で、未コミット変更、未追跡ファイル、端末固有のGit設定は別途扱う。Git LFSやサブモジュールを使うリポジトリは追加のデータ転送も検討する。記事には実際の認証情報や接続先を載せず、bundle自体も履歴に機密情報を含み得るファイルとして扱う。

今回確認したのは、サーバ上の競合解消とマージ確定、そしてMacへの履歴の統合。シェル設定の実行時動作と最終pushの成功は、それぞれ別の確認項目として残る。
