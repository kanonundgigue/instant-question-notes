CPUとGPUの違いは？計算機ユーザの視点から

作成日: 2026-07-31

更新日: 2026-07-31

カテゴリ: productivity

元の質問

CPUとGPUの違いは？計算機ユーザの視点から教えて

回答

CPUは、分岐や依存関係のある処理を含む少数の仕事を、短い待ち時間で進めることが得意な汎用プロセッサです。GPUは、同種の計算を大量のデータへ並列に適用し、単位時間あたりの総処理量を増やすことが得意です。実際のアプリケーションは、CPUを司令塔、GPUを並列演算器として組み合わせる構成が基本です。CUDAのプログラミングモデルでも、アプリケーションはCPUで開始し、CPU側がデータ転送とGPU上の計算開始を制御する異種混合システムとして説明されています。[1]

まず押さえる要点

  • CPUは応答時間重視: OS、入出力、逐次処理、複雑な分岐、小規模な処理に向く。
  • GPUは総処理量重視: 行列演算、画像処理、深層学習、格子計算など、大量の要素へ似た演算を行う処理に向く。
  • GPUが常に速いわけではない: 計算が小さい、並列化しにくい、データ転送が多い、GPUメモリに収まらない場合は利点が小さくなる。
  • CPUコア数とGPUの演算器数は直接比較しない: 「GPUは数千コアだからCPUの数百倍」という読み方はできない。
  • 選定は実測で決める: カタログ上の演算性能ではなく、前処理・転送・計算・後処理を含む処理全体の時間を比較する。

設計思想の違い

観点 CPU GPU
主な目標 少数の仕事を早く終える 多数の仕事をまとめて処理する
並列性 比較的少数の強力なコアを使う 非常に多数の軽量スレッドを走らせる
制御 分岐、逐次依存、異なる種類の仕事に強い 同じ命令列を多数のデータへ適用すると効率がよい
メモリ利用 大きなキャッシュで待ち時間を減らす 高い帯域と多数スレッドで総処理量を稼ぐ
典型的な役割 制御、前処理、I/O、逐次部分 計算量の大きい並列部分

NVIDIAのBest Practices Guideは、この違いを「CPUコアは少数スレッドのレイテンシ（処理を依頼してから終わるまでの待ち時間）を小さくし、GPUは多数の軽量スレッドによるスループット（単位時間あたりの総処理量）を大きくする」と整理しています。[2]ここで重要なのは、GPUの個々の演算器がCPUコアの縮小版なのではなく、両者の「コア」が異なる設計単位だという点です。

では「CPUのベクトル計算」はどこに入るか

CPUにも、1命令で複数のデータ要素を処理するSIMD（Single Instruction, Multiple Data）演算器があります。Intel CPUのSSE、AVX、AVX2、AVX-512などがその例です。たとえばAVXは256ビット、AVX-512は512ビットのベクトルレジスタを使い、複数の浮動小数点数や整数へ同じ演算を一度に適用できます。[6]これは「CPUかGPUか」という二択ではなく、CPUコア内部にもデータ並列性があることを意味します。

一方、計算機分野でいう「ベクトル計算機」または「ベクトル型スーパーコンピュータ」は、ベクトル演算を補助機能ではなく中心機能として設計した計算機を指すことがあります。たとえばNEC SX-Aurora TSUBASAのVector Engineは、大容量のベクトルレジスタと高いメモリ帯域を備え、1本のベクトル命令で多数の要素を処理します。現在のSX-Auroraは、OS機能を主に担うx86のVector Hostと、アプリケーションを実行するVector Engineを組み合わせた構成なので、一般的なCPU内SIMDとは区別した方が正確です。[7]

方式 並列化の単位 計算機ユーザから見た特徴
CPUのスカラー処理 命令・スレッド 分岐や逐次依存を含む汎用処理に強い
CPUのSIMD 1命令内の複数要素 通常のCPUメモリ上で、配列ループを高速化できる
専用ベクトルプロセッサ 長いベクトル命令 長い配列と高メモリ帯域を使う大規模計算に強い
GPUのSIMT 多数の軽量スレッド 極めて多くの独立要素を同時処理しやすい

CPUのSIMDとマルチコアは併用できます。各コアが配列の一部分を担当し、そのコア内ではベクトル命令が複数要素をまとめて処理します。長く連続した配列、規則的なメモリアクセス、反復間の依存が少ないループはベクトル化しやすく、分岐や不規則アクセスが多いループは効率が下がりやすいです。Intelのコンパイラ資料でも、ループの演算内容や依存関係が自動ベクトル化の可否を左右すると説明されています。[8]

CPUベクトル計算とGPUをどう選ぶか

  • まず最適化済みCPUライブラリを使う: NumPyや線形代数ライブラリを使う計算では、その内部でSIMDやマルチコアが利用されている場合がある。
  • 自作ループはベクトル化を確認する: CやFortranでは、コンパイラのベクトル化レポートを見て、対象ループが実際にベクトル命令へ変換されたか確認する。
  • データがRAMにあり計算が中規模ならCPU SIMDも有力: GPUへの転送を追加せず、低い起動コストで処理できる。
  • メモリ帯域が支配的な長い配列なら専用ベクトル機を検討する: 気象・流体・格子計算など、演算より大量データの読み書きが律速になる処理と相性がよい。
  • 独立要素が非常に多く、GPU上で計算を継続できるならGPUを検討する: 転送コストを回収できるだけの演算量と並列度が必要になる。

実務上の判断順は、逐次CPU版 → CPU内SIMD → マルチコアとSIMDの併用 → GPUオフロードと考えると整理しやすくなります。専用ベクトル計算機を利用できる環境では、CPUとGPUの間にもう一つの有力な選択肢がある、と捉えます。

計算はどこを通るのか

独立GPUを使う典型的な計算では、データは次の順に移動します。

  1. ストレージからCPU側のRAMへ入力を読む。
  2. CPUで読み込み、整形、条件分岐などの前処理を行う。
  3. 必要な配列をGPU側のVRAMへ転送する。
  4. GPU上でカーネルと呼ばれる並列計算を実行する。
  5. 必要な結果をRAMへ戻し、CPUで保存や表示を行う。

CPU側のRAMとGPU側のVRAMが物理的に分かれたシステムでは、この間の転送が必要です。一方、統合GPUやSoCでは物理メモリを共有する構成もありますが、プログラミング上のCPU側とGPU側という区別が残る場合があります。[1][2]

どのような処理が向いているか

処理の特徴 第一候補 例
小規模、逐次的、分岐が多い CPU ファイル処理、表形式データの整形、OS処理
同じ演算を大量の要素へ適用 GPU 行列積、畳み込み、画像変換、格子計算
小さな計算を一度だけ実行 CPU 小配列の集計、短いスクリプト
大きな配列を繰り返し計算 GPUを検討 深層学習、反復的な線形代数、アンサンブル計算
外部ライブラリがGPU非対応 CPU GPUバックエンドのない既存コード

GPUが特に有利なのは、多数のデータ要素を同時に処理でき、転送したデータに対して十分な量の計算を行える場合です。逆に、転送量に対して演算が少ない処理では、GPUの演算そのものが速くても、処理全体は速くならないことがあります。GPU向けの公式ガイドも、転送時間を性能評価に含め、データを可能な限りGPU側に保持し、小さな転送を繰り返さないよう推奨しています。[2][3]

GPUを使っても速くならない主な理由

  • 仕事が小さすぎる: GPUへ計算を依頼する準備時間の割合が大きくなる。
  • CPU–GPU転送が多い: ループのたびに配列を往復させると、転送が支配的になる。
  • 並列化できる部分が少ない: 逐次部分はGPUを追加しても短くならない。
  • スレッドごとの分岐がばらばら: 同時に動くスレッドが異なる経路を通ると、GPUの並列実行効率が落ちる。
  • VRAMが不足する: 問題を分割したりCPU側へ退避したりすると、追加の転送と管理が必要になる。
  • 必要な精度が重い: GPUや世代によって倍精度演算の性能は大きく異なるため、科学計算では単精度のピーク性能だけで選ばない。[5]
  • ソフトウェアが対応していない: GPU対応ドライバ、ライブラリ、演算実装がなければ、コードを書き換えるだけでは利用できない。

計算機ユーザとしての選び方

  1. まずCPU版を正解の基準にする。 小さな入力で結果を確認し、再現可能な基準実装を持つ。
  2. 処理時間の内訳を測る。 全体で時間を使っている箇所が行列演算なのか、I/Oや前処理なのかをプロファイラで確認する。
  3. GPU対応ライブラリを確認する。 自作GPUカーネルより先に、利用中の線形代数、機械学習、配列ライブラリに対応バックエンドがあるか調べる。
  4. 問題がVRAMに収まるか見積もる。 入力だけでなく、中間配列、勾配、作業領域も必要になる。
  5. 処理全体を同じ条件で測る。 データ転送を含む時間と、GPU上の計算だけの時間を分けて記録する。
  6. 結果の差も検証する。 浮動小数点演算は計算順序が変わると丸め結果も変わり得るため、CPU版とGPU版の完全一致だけを合格条件にしない。[5]

PythonでCPU時間とGPU時間を測る例

次はPyTorchで同じ行列積を測る最小例です。GPUの計算だけを測った値と、CPUからGPUへの転送・結果の回収を含む値を分けます。GPU演算は通常非同期なので、単純に呼び出しの前後だけを測ると、計算完了前に時計を止めてしまいます。正確な時間測定には同期が必要です。[4]

from time import perf_counter

import torch


def measure_matmul(size: int = 2048, repeats: int = 5) -> dict[str, float]:
    """CPUとCUDA GPUで行列積の所要時間を測る。

    Parameters
    ----------
    size
        正方行列の一辺の要素数。
    repeats
        行列積を繰り返す回数。

    Returns
    -------
    dict[str, float]
        CPU、GPU計算のみ、転送込みGPU処理の秒数。
    """
    if not torch.cuda.is_available():
        raise RuntimeError("CUDA対応GPUを利用できません。")

    a_cpu = torch.randn(size, size, dtype=torch.float32)
    b_cpu = torch.randn(size, size, dtype=torch.float32)

    # CPU版を測る
    _ = a_cpu @ b_cpu
    started = perf_counter()
    for _ in range(repeats):
        c_cpu = a_cpu @ b_cpu
    cpu_seconds = perf_counter() - started

    # GPU上の計算だけを測る
    a_gpu = a_cpu.to("cuda")
    b_gpu = b_cpu.to("cuda")
    _ = a_gpu @ b_gpu
    torch.cuda.synchronize()
    started = perf_counter()
    for _ in range(repeats):
        c_gpu = a_gpu @ b_gpu
    torch.cuda.synchronize()
    gpu_compute_seconds = perf_counter() - started

    # CPUからの転送と結果回収を含む処理全体を測る
    torch.cuda.synchronize()
    started = perf_counter()
    a_gpu = a_cpu.to("cuda")
    b_gpu = b_cpu.to("cuda")
    for _ in range(repeats):
        c_gpu = a_gpu @ b_gpu
    c_result = c_gpu.cpu()
    gpu_end_to_end_seconds = perf_counter() - started

    # 計算結果を使い、CPU版とGPU版の先頭要素も確認する
    _ = (c_cpu[0, 0].item(), c_result[0, 0].item())

    return {
        "cpu_seconds": cpu_seconds,
        "gpu_compute_seconds": gpu_compute_seconds,
        "gpu_end_to_end_seconds": gpu_end_to_end_seconds,
    }


print(torch.cuda.get_device_name())
print(measure_matmul())

出力値はGPU、CPU、PyTorch、行列サイズによって変わるため、固定の模範値はありません。実運用では複数回測って中央値を使い、実際の入力サイズでも確認します。また、この例のGPU計算時間は「入力がすでにVRAMにある」条件です。アプリケーション全体の速さを判断するときは、転送込みの時間を無視しません。

まとめ

CPUとGPUの違いは、単純な速さではなく、CPUが複雑な少数の仕事の待ち時間を減らし、GPUが単純化できる大量の仕事の総処理量を増やすよう設計されていることです。ただしCPUもSIMD命令でベクトル計算でき、専用ベクトルプロセッサという別系統の計算機もあります。計算機ユーザは、処理の並列性、データ量、メモリ帯域、VRAM、転送回数、対応ライブラリ、必要精度を見て使い分けます。最終判断は、CPUとGPUを対立させるのではなく、CPU内ベクトル化も含めて各段階を実測し、GPUへ渡す価値があるボトルネックだけを移して行います。
